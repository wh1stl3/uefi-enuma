Packaging must tag the image hardware_review=R-005; the companion runner rejects pending/missing approval or a non-matching image before calling any device tool.

The transaction decodes a descriptor, requires source width>=128 and height>=8 and validates the complete cropped span in [0x9c000000,0x9e300000). It first synchronizes each selected row before saving exactly 128x8 32-bit words (4096 bytes) in caller stack scratch outside the display reservation, then obtains and compares a second decoded descriptor before any store. It writes only that 128x8 window all-white, synchronizes each row, requests 500000us Stall, restores every saved word even if Stall returns an error, synchronizes rows and reads back every saved word. Normal maximums: 96 read-only display-register reads, 2048 pixel reads, 2048 pixel stores (paint plus restore), 24 row cache synchronizations (before backup, after paint, after restore). No new heap allocation, library/constructor, memory field, register store, mode setting, partition operation or verification flag.

The ARM synchronization helper derives cache line size from CTR_EL0, uses DC CIVAC on intersecting lines and DSB SY before/after. Rounded lines remain inside the existing display reservation (both bounds aligned to the largest representable line size); this can clean neighboring unchanged bytes, but pixel stores remain in the exact small window. The existing display mapping is WRITE_THROUGH_XN. Cache primitives and timer behavior are newly runtime-untested in this caller; host/object qualification is not hardware proof.

All-white avoids assuming RGB channel order, but the selected descriptor may be stale/inactive or its register address may be an IOVA. Writing the numerically bounded address as physical RAM can therefore produce no visible mark. The operation remains constrained to existing display-reserved RAM; neither drawing nor IOVA identity is claimed before observing the screen. CPU exceptions or a hung read/cache/Stall callback can prevent software restoration. The synchronous Core fallback is not a watchdog; manual recovery remains required if return fails. A successful recovery still requires Android completion/root/original partition checks and actual no-button evidence.

Host fake-memory scenarios cover boundary/alias refusals, descriptor changes before stores, normal save/paint/restore/readback, wait errors and readback corruption. Actual AArch64 objects include local 4096-byte scratch and cache instructions, with only the existing gBS external. Full FD/build/boot-v3 qualification and a concrete image digest remain prerequisites to execution despite the recorded approval.
